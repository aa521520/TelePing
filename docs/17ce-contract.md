# Independent 17CE bot contract

User request, 2026-11-04: a second Telegram bot in the existing private group, for official 17CE only. Independent target list, bulk add/delete (one URL per line), list, check all, temporary one/many target checks, operator/region selection, editable daily defaults and frequency. Default 1440 minutes. User explicitly selected no spending limit. Initial deployment has no 17CE API credentials; real protocol and billing acceptance require an active official account. All commands still require the group's current human owner/admin. Buttons open an input/selection/confirmation step.

## Boundaries and deployment

Create `cloudflare17ce/worker.mjs` with class `SeventeenCE`, an independent SQLite DO namespace and Worker `teleping-17ce`. It may import the existing pure AES/normalization/chunk helpers from `../cloudflare/core.mjs`, but must not change the first bot or use its state namespace. State AES purpose is `17ce:state`. New independent STATE_ENCRYPTION_KEY, WEBHOOK_SECRET and RUNNER_API_TOKEN; existing repo-scoped Actions dispatch credential can be reused with unchanged scope. Fixed official provider WSS host; "change API" means replace official username/API token, not arbitrary endpoint execution.

`scripts/seventeence-provider.mjs` owns the official WS protocol. `scripts/seventeence-runner.mjs` owns the authenticated service client/CLI. GitHub workflow `17ce.yml` uses Node 24 and runs one sequential claim of at most 20 jobs, at most 120 minutes. CF keeps the queue and schedules subsequent claims. No browser or provider credential is ever logged, put in job names, or written to an artifact; encrypted plan is decoded only in runner memory. Public output is counts and fixed codes.

## Profile and result schema

Profile is {test_type:"HTTP",operators:[1,2,7],area:1,provinces:[],cities:[],node_type:1,nodes_per_region:1}. Operator IDs must be documented; area is 1/2/3, node_type 1..5, nodes_per_region 1..3. Province/city IDs are 17CE IDs, not national administrative codes. Operator result keys are string ISP IDs or "unknown"; values are {node_count,success_count,failure_count,avg_seconds,max_seconds}. Counts are nonnegative integers <=10000 and timings finite nonnegative numbers or null. TaskId is a string <=200 characters without control characters. A TaskEnd with zero nodes is failed/no_results; a completed task with some failed nodes remains status=complete and its failure counters communicate the network outcome.

## Runner API

GET /health -> {ok:true,service:'teleping-17ce'}.
POST /telegram authenticated via X-Telegram-Bot-Api-Secret-Token. Filter irrelevant chats, bots and anonymous messages before durable acceptance; allow only trusted group migration fields related to bound chat, plus currently authorized private setup sessions. Recent update-ID dedup (not high-water only), encrypted inbox before 200 and capacity limit with retriable refusal.

All /api/* POST routes require Bearer RUNNER_API_TOKEN, bounded JSON and fixed error codes. Runner run ID regex `^[1-9][0-9]{0,29}-[1-9][0-9]{0,9}$`. Completed receipts max64 plus numeric run-attempt high-water fencing. Provider work never begins from /api/setup.

- /api/setup {}: delete native default and bound-chat command menus, enqueue Chinese function panel, return {ok:true}. Must not erase list/history or set webhook.
- /api/claim {run_id,executor_id}: return {should_check:false} when not ready/idle/busy. Otherwise {should_check:true,payload:string}, AES purpose `17ce:plan:<run_id>`. Plan {run_id,executor_id,lease_token,expires,config_version,credentials:{username,api_token},jobs:[{id,target,generation,round_id,profile}]}. Snapshot up to20 queued jobs and lease for 130min. Each runClaim invocation generates a fresh executor_id UUID. Only the same run+executor can repeat claim idempotently; another executor for an active run gets should_check:false. Active same-executor duplicate claim returns original encrypted plan; completed duplicate returns idle. No force flag bypasses API readiness or channel confirmation.
- /api/begin {run_id,executor_id,lease_token,job_id}: atomically persist status=begun before {permit:true}; return {permit:false} for repeats, cancellation, stale configuration/generation/lease. The runner calls this AFTER WS authentication and immediately BEFORE sending SpeedRequest. A failed/ambiguous begin response is never permission to submit. No paid job is begun twice.
- /api/event {run_id,payload}: encrypted purpose `17ce:event:<run_id>`. Plaintext {run_id,executor_id,lease_token,job_id,event_id,kind,result}. kind `accepted` stores known TaskId, kind `terminal` finalizes one job. result {status:'complete'|'failed'|'uncertain'|'blocked',task_id?:string,node_count:number,success_count:number,failure_count:number,operators:object,error_code?:string}. Operator values only bounded counters and average/max seconds; no raw headers/bodies. Event IDs are fixed `<job_id>:accepted` and `<job_id>:terminal`; retries are idempotent. Only claimed jobs in that lease are mutable, and late deleted targets must not return to the list. Terminal event marks receipt before notification enqueue. Store bounded recent job history, not full plans forever.
- /api/finish {run_id,executor_id,lease_token}: mark the claim completed; any claimed-but-unbegun jobs return to queue, begun-without-terminal become uncertain and never auto-submit again. Clear lease and schedule remaining queue. Duplicates idempotent only for the matching executor receipt. All mutation APIs verify the executor_id as well as lease token. A late accepted event after terminal may supplement a valid TaskId but never change terminal status, notify again or resubmit. Lease expiry follows the same rule, not ordinary browser retry policy.

## Official WS adapter

See `17ce-research.md`. Fixed `wss://wsapi.17ce.com:8001/socket`, authentication query user/code/ut; code MD5(Base64(MD5(api_token)[4:23]+trim(username)+timestamp)). No AuthRequest JSON unless official evidence requires it. Wait for auth rt=1, then call begin permit, then send one type=1 HTTP request. Use the current official example field representation; never retry alternate formats with billable requests. One WS connection per queued target, sequential execution. Timeout <=240 seconds per job. API account restrictions cannot be live-tested before user activates account.

Collect TaskAccept/NewData/TaskEnd/TaskErr using txnid matching and NodeID dedup. HTTP 2xx/3xx are successful node results; failed codes and explicit errors are failures; missing data is not success. After a submission, a disconnect/timeout/no definitive TaskEnd yields uncertain and is never automatically resubmitted, even if no TaskId was received. Before any submission, auth/connect failure may be reported blocked/failed without claiming it consumed money. Provider raw messages and WS authentication URL must never appear in logs or thrown public errors. Fixed error enums only.

Validate TaskEnd.TotalCount against received unique nodes and known allocation; it is consistency evidence, not an established billing count. Missing results or conflicting task identifiers/counts produce uncertain/provider_result_incomplete. If the allocated count conflicts, terminal allocated_node_count is explicitly null, overriding an earlier accepted value. If allocation and TotalCount agree but fewer node results arrived, retain allocation for the reference estimate but mark the network result incomplete. Matching TaskErr/TaskEnd may supply a non-conflicting TaskId for reconciliation. Never retry a paid submission to resolve these discrepancies.

## Reporting revision: one report per user/daily round

User approved round summaries plus abnormal-target details instead of one message per target. A round is the complete user-confirmed target set or one scheduled daily target set, NOT a GitHub claim of at most20 jobs. Aggregate across all claims belonging to round_id. Persist aggregation with the existing event receipt; duplicates must not double counts, charges or notifications. Keep begun/TaskId journaling and all executor/generation guards intact.

Track round metadata at enqueue: id, created time, source, total target count, frozen profile and reference unit price. The same round may span many workflows. Normal targets only contribute counts; abnormal/failed/uncertain/cancelled targets contribute bounded details and node/carrier counters. Do not emit per-target terminal or lease-expiry messages. Emit one completed summary when no pending jobs for that round remain, then abnormal details split into <=3500 UTF-16 chunks as necessary. All-normal round emits only the summary. If authentication pauses a round indefinitely, send a clearly marked partial/paused summary once (remaining targets included); after configuration recovery the final report can complete the round. No periodic unchanged progress messages.

Deletion and configuration cancellation must account for unbegun jobs, so a round cannot wait forever on removed work. Begun deletion still waits for terminal/uncertain and keeps charge metadata. Unrelated rounds, newly queued requests and simultaneous profile choices must not merge. Existing deployed state may lack rounds/extended result fields: migrate conservatively without resetting jobs, credentials, defaults or receipts. If old completed information is unavailable, mark incomplete rather than invent totals. Retain bounded recent completed rounds and compact old state; never retain full normal node bodies or full plans indefinitely.

Financial reporting: public official evidence still provides no balance/actual-debit endpoint. Remove all repeated balance/cumulative-unknown footers from ordinary menu, command, and report messages. Each resulting report chunk ends with the same clearly labelled *round total estimate*, not an amount to add across pages. Use a fixed per-round snapshot of reference price, default 10000 micro-yuan = CNY0.01 per node/test; deployment variable REFERENCE_NODE_PRICE_MICRO may configure a different nonnegative integer reference price. Say reference/estimate, never actual paid or balance. No provider billing requests or account scraping are introduced.

Runner terminal and accepted events gain optional whitelisted fields `allocated_node_count` (integer0..10000 or null) and `submitted` (boolean). Provider sets submitted true immediately before the single socket.send attempt; false means no SpeedRequest was attempted. Parse official nested TaskAccept.data[task-key] for matching txnid, TaskId, nodeCount, and nodes[node-id].nodeinfo.isp; preserve allocated count and node/carrier mapping. Support the previously accepted direct TaskAccept shape too, but never retry a paid request to probe formats. Terminal always carries the facts collected before an accepted callback, even when that callback fails. Missing fields from old runners are unknown, not zero.

Estimate primarily uses accepted allocated-node counts. If a submitted task lacks that receipt, use only unique received nodes as an explicitly incomplete reference estimate. An unsubmitted/cancelled-before-submit target contributes zero. A submitted/ambiguous task with no known node count must flag unconfirmed cost, never display an exact zero total. Failed/timed-out nodes may be billed; do not deduct them. Explain that the reference price and provider settlement may differ. Partial estimates must state known node count and number of unconfirmed tasks; if no priced nodes are known but unresolved submissions exist, display fee pending rather than a fake exact amount.

Summary should distinguish normal targets, targets with failed nodes, detection failures, uncertain submissions, and cancellations; completing a provider task is not proof all nodes succeeded. Show aggregate selected channels/node counts, concise abnormal details and TaskIds only where reconciliation matters. Actual no-node and authentication failures must not be described as domain network failures. Update the Chinese guide and fixtures accordingly; synthetic previews must be labelled simulated and never sent as a real paid result.
